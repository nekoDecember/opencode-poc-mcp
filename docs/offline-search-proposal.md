# 外部検索サービスを使わない機能制限版の案

作成日: 2026-11-16。これは提案であり、現行コードの検索実装はまだTavilyのまま。

## 提案する構成

一般Web検索を、登録した公式資料を対象とするローカル全文検索へ置き換える。検索サービスの契約・APIキー・月間の検索枠をなくし、情報源の取得先だけを人が設定する。

主な用途であるOSSの仕様、設定、API、例外の調査に対象を絞る。最初はPython、Playwright、Docker等、実際に使う数製品から始める。検索対象は、取得・保存が認められる公式ドキュメント、公開リポジトリの資料、ソースコード、リリースノートとする。

1. 人が取得元URL、製品名、対象バージョン、対象ディレクトリを設定する。
2. 明示的な更新操作で資料を取得し、ローカルへ保存する。Gitで配布される資料を優先する。
3. 見出しや関数などの単位で索引を作り、SQLiteへ保存する。
4. OpenCodeが製品・検索語・必要ならバージョンを指定する。
5. MCPが該当箇所の抜粋、見出し、出典URL、バージョン、取得日時を返す。
6. OpenCodeが結果を読み、解釈と文章化を行う。MCPから別のLLMは呼ばない。

検索はローカルで完結する。更新時も、質問文や検索語をURL・Git引数へ埋め込まない。取得先・範囲の登録を変更するMCPツールは設けない。

## 検索精度を出す方法

現在の`repo_search`は固定文字列を含む行を返す機能なので、それだけでは関連度順の資料検索にならない。次の小さな拡張を入れる。

- **製品とバージョンで絞る。** 似た名前の別製品や、異なる版の仕様を混ぜない。
- **短いまとまりを検索する。** ページ全文を一件として扱わず、見出し本文・コード例・関数の周辺を対象にする。元の見出しと出典の位置を保持する。
- **関連度順に返す。** BM25を基本とし、タイトル・見出しを重くする。例外名、エラーコード、API名の完全一致を優先する。
- **検索語の表記を整える。** 日本語の分割と、`locator.click`など記号を含む識別子を扱う。設定に登録した略称・別名も使えるようにする。
- **見つからない場合を明示する。** 「登録資料内では見つからない」と返す。一般Web全体に答えがないとは扱わない。

SQLite FTS5は全文検索、BM25、列ごとの重み付け、抜粋生成を備えている。日本語の分割や識別子の扱いは、索引を作る前の処理で補う。追加の検索用コンテナやベクトルDBは置かない。[SQLite公式資料](https://www.sqlite.org/fts5.html)

「対象資料に答えが載っている質問なら、その箇所を上位へ出す」という精度を狙う。一般Webの広い範囲から新しい情報源を発見する能力は削る。実データでの精度はまだ測定していない。

## 得意な調査と失う機能

| 調査 | この案での扱い |
| --- | --- |
| 製品の仕様・設定・API | 公式資料を収集できれば主な対象にできる |
| API名・例外名・エラーコード | 完全一致を優先して調べられる。ただし資料に解説がないものは回答根拠が不足する |
| バージョン変更・廃止機能 | 対象版の資料とリリースノートを保存して調べる |
| 未知の不具合、Issue、個人ブログの解決策 | 収集していなければ見つからない。一般Web横断検索は提供しない |
| 企業情報・ニュース | 登録済み企業の保存資料に限定する。速報や未知の企業の発見には向かない |
| 社内の知識・日報 | 既存のGit参照機能を引き続き使う。今回の公開資料検索への置き換えは不要 |

企業情報や最新情報が必要でURLが分かっている場合は、既存のブラウザ操作でそのページを参照できる。これを一般Web検索と同等とは扱わない。

## 実装範囲

PythonとSQLiteを使い、今のMCPコンテナへ追加する。Dockerネットワーク、スクリーンショット、Git保存、日報、ブラウザ操作の構成は維持する。

| ツール案 | 用途 |
| --- | --- |
| `docs_update(source_ids)` | 登録した資料の取得・更新と索引作成。検索語は受け取らない |
| `docs_search(source_ids, terms, version, limit)` | ローカル索引だけを検索する |
| `docs_read(result_id)` | 保存済みの該当節と前後の本文を読む |

検索例:

```json
{
  "source_ids": ["playwright"],
  "terms": ["TimeoutError", "locator.click"],
  "version": "1.58",
  "limit": 5
}
```

`terms`はローカル処理にしか使わないため、外部検索用の公開語IDに限定する必要はない。従来の「自由文を外部へ送らない」要件は維持する。

資料と索引は既存の永続volume内へ保存する。更新は依頼時だけとし、常時監視・自動巡回・一般Webのクローラーは作らない。外部への接続がない検索処理に、契約による月間回数枠はない。資料の取得・更新には、配布元の利用条件とアクセス制限が適用される。

## 確認方法

普段調べる内容を10〜20件用意し、回答箇所が登録資料にあることを確認したうえで検索する。上位5件に回答箇所が入るか、別製品・別バージョンを誤って返さないかを見る。質問に対応する資料を持っていないケースは、順位付けの失敗と分けて記録する。

最初から意味検索やローカルの埋め込みモデルを加えず、この確認で不足が分かった部分だけを改善する。

## SearXNGを第一案にしない理由

外部検索エンジンを束ねるSearXNGの構成では、自前で動かしても検索語の送信先は外部に残る。Google向け実装もWeb上の結果取得とCAPTCHAへの対応を含む。今回の「外部検索サービスへの依存を避ける」「検索結果ページの無断スクレイピングを前提にしない」という方針には、登録資料のローカル検索の方が合わせやすい。[SearXNG公式実装資料](https://docs.searxng.org/dev/engines/online/google.html)
